# Проверка работы native-режима

Инструкция для ревизии `0.15.0.3`: как убедиться, что мост поднялся, инструменты
видят правильный проект и пул процессов работает по каталогам сессий.

Проверка делится на две части: **автоматическую** (5 минут, без DSH-сессии) и
**живую** (в DSH, две сессии на двух проектах). Первая ловит поломки установки и
рантайма, вторая — единственное, что автоматика проверить не может: что
`ctx.workingDirectory` отдаёт каталог именно этой сессии.

---

## 0. Быстрый чек-лист

| # | Шаг | Где |
|---|---|---|
| 1 | `node host/selftest.js --cwd <проект>` → `ok: true`, `tools: 11` | терминал |
| 2 | `node install.mjs --verify` → `native check : ok … workspace …` | терминал |
| 3 | В патче профиля есть `unica-native` и **нет** `mcp-unica` | файл профиля |
| 4 | После рестарта DSH: `unica.view {}` в сессии возвращает её каталог | DSH |
| 5 | Две сессии в разных проектах → разные `workspaceRoot` и разные результаты `unica.search` | DSH |

Если все пять — зелёные, native-режим работает.

---

## 1. Автоматическая часть

Все команды — из каталога `dsh-unica-plugin/`.

### 1.1. Сам мост, без DSH

```sh
node host/selftest.js --cwd /путь/к/проекту
```

Ожидаемый вывод:

```json
{
  "ok": true,
  "cwd": "/путь/к/проекту",
  "root": "/путь/к/проекту",
  "tools": 11,
  "ms": 408,
  "server": { "name": "unica", "version": "0.15.0-rc.1" }
}
```

- `ok: true` — unica поднялась, каталог совпал;
- `tools: 11` — каталог инструментов на месте;
- `ms` — время старта (холодный кэш — секунды, тёплый — сотни мс).

Проверка независимости каталогов — два процесса параллельно:

```sh
node host/selftest.js --cwd /путь/к/проекту-А &
node host/selftest.js --cwd /путь/к/проекту-Б &
wait
```

У каждого должен быть свой `root`, совпадающий с его `cwd`.

### 1.2. Установщик

```sh
node install.mjs --dry-run                 # только план, ничего не пишет
node install.mjs --verify --verify-cwd /путь/к/проекту
```

Ожидаемо во втором:

```
  native check  : ok      serverInfo unica 0.15.0-rc.1, 11 tools in … ms, workspace /путь/к/проекту
```

Если `--verify` пишет `FAIL`, см. раздел 5.

### 1.3. Проверки самого порта

```sh
node tools/check-tool-names.mjs   # 666 ссылок, 11 имён, все резолвятся
node tools/ci-dryrun.mjs          # патч → композиция DSH → миграция → платформа
```

`ci-dryrun` должен закончиться `CI job dry-run passed`. Он же проверяет, что
при установке старый `mcp-unica` вычищается.

## 2. Установка в рабочий профиль

```sh
# DSH Desktop
node install.mjs --target preset --profile desktop --verify

# Web GUI / headless
node install.mjs --target both --verify
```

Установщик пишет в патч профиля строку `unica-native` с `file://`-URL на
`host/index.js` и удаляет легаси-строку `mcp-unica`, если она была.

Проверить содержимое патча (путь зависит от профиля):

```sh
grep -n "unica-native\|mcp-unica" ~/.dsh/profiles/desktop/cordis.patch.yml
grep -n "unica-native\|mcp-unica" ~/.dsh/profiles/headless/cordis.patch.yml
```

Ожидание: строки `unica-native` есть, `mcp-unica` — **нет** (иначе два источника
зарегистрируют одинаковые имена).

> `dsh --profile desktop --dump-config` намеренно отказывает («managed exclusively
> by the Electron application»), поэтому desktop-профиль проверяется по файлу и
> живой сессией. Для `web`/`headless` можно и так:
> `dsh --profile headless --dump-config | grep -A3 unica-native`.

**Перезапустите DSH** — патч профиля читается при старте — и откройте новую
сессию на пресете **«Unica 1C»**.

## 3. Живая проверка в DSH

### 3.1. Один проект

Откройте сессию в каталоге проекта и попросите:

> Вызови `unica.view {}` и покажи поле `workspaceRoot` из ответа.

Ожидание: `workspaceRoot` — абсолютный путь каталога, в котором открыта сессия
(а не `~/.dsh/profiles/...` и не другой проект).

Быстрый признак правильного моста: в ответе `workspaceRootOrigin.channel` =
`launchCwd`, а `requestedDirectory` — каталог сессии.

### 3.2. Два проекта — главная проверка

1. Создайте **две сессии** DSH в двух разных каталогах (проект А и проект Б).
2. В каждой выполните тот же промпт `unica.view {}`.
3. Сравните `workspaceRoot`: у А — каталог А, у Б — каталог Б, одновременно.

Затем — проверка поиска по своей кодовой базе. В каждой сессии:

> Вызови `unica.search` с `{"query": "<символ, который есть только в этом проекте>", "corpus": "text"}`
> и покажи, какие файлы нашлись.

Ожидание: в сессии А находятся только файлы А, в сессии Б — только Б. Это и есть
тот дефект, ради которого убирали MCP-строку.

### 3.3. Остальные инструменты

| Промпт | Ожидание |
|---|---|
| `unica.check` на модуле проекта | `validators: ["bsl"]`, `status: passed` (первый вызов может прогревать индекс — повторить) |
| `unica.run` с `dryRun: true` | план и `taskId`; затем `unica.task.result` по нему |
| `unica.diff` двух узлов | `equal: false` и `changes` |
| навык `code-search` / `cf-edit` | работает на выбранном проекте |

### 3.4. Пул процессов (по желанию)

```sh
pgrep -f "bootstrap/launch.mjs" | while read p; do
  printf "%s " "$p"; lsof -a -p "$p" -d cwd | tail -1 | awk '{print $NF}'
done
```

Ожидание: по процессу на каждый каталог, в котором реально работали; после
`idleMs` (10 минут) без вызовов процессы завершаются.

## 3.5. Проверка записи и платформенных операций

Сделано на rc.5 в проекте `DSH_Test2`; повторяется за 10 минут.

**Метаданные (навык `meta-add`).** План → `executionToken` → исполнение → чтение:

1. `unica.apply` с `object.create` даёт план и `executionToken`, на диске ничего не меняется.
2. Повторный вызов только с токеном публикует изменения: появляются
   `src/Catalogs/<Имя>.xml` и `Ext/ObjectModule.bsl`, объект виден в `unica.view`
   и в `<ChildObjects>` корня.
3. `unica.check` по объекту — `status: passed`, `validators: ["meta"]`.

**Контракт типов изменился в rc.5.** Тип реквизита-числа теперь
`{"kind": "number", "digits": 15, "fraction": 2, "sign": "any"}` —
`decimal` с `precision`/`scale` больше не принимается. Навыки намеренно не
хардкодят схему: перед вызовом читайте контракт операции по адресу
`<узел>.Can.<операция>`, иначе ошибка будет `unsupported type kind` или
`` `digits` must be an unsigned 32-bit integer ``.

**Платформа (1С 8.3.27.2342, macOS arm64).** Все операции проходят, но чувствительны к лицензии:

| Операция | Итог |
|---|---|
| `unica.run` `make` (`output: build/out/<Имя>.cf`) | ok, `.cf` собран |
| `unica.run` `infobase.create` | ok, файловая база создана из исходников |
| `unica.run` `push` (инкрементальный, после правки метаданных) | ok, `providerDispatched: true`, состояние подтверждено провайдером |
| `unica.run` `download` (`state: database`) | ok, `.cf` выгружен и проверен |
| проверка результата | `1cv8 DESIGNER /DumpConfigToFiles` показывает в базе все объекты исходников |

**Если push/download падают — сначала проверьте лицензию.** Без активированной
лицензии те же вызовы отвечают `credentials_rejected` (`the designer agent
rejected the infobase user … user ''`) и `platform export failed … platform log
read error`. Это не credential-проблема и не дефект моста: платформа в таком
сеансе сообщает о себе в `/Out`-логе —

```
Запуск системы выполнен без использования аппаратной лицензии (ключа защиты).
```

Проверить одной командой:

```sh
/opt/1cv8/8.3.27.2342/1cv8 DESIGNER /F<путь к базе> /CheckConfig /Out/tmp/1c.txt
cat /tmp/1c.txt
```

Если в логе есть строка про отсутствие лицензии — активируйте её и повторите
`unica.run`: после активации `push` и `download` прошли без изменений в проекте.
Диагностическое правило: `credentials_rejected` на файловой базе без
пользователей почти всегда означает лицензию, а не логин.

## 4. Критерии приёмки

| # | Проверка | Проходит, если |
|---|---|---|
| 1 | `host/selftest.js` | `ok: true`, `tools: 11`, `root === cwd` |
| 2 | `install.mjs --verify` | `native check : ok … 11 tools … workspace …` |
| 3 | Патч профиля | `unica-native` есть, `mcp-unica` нет |
| 4 | Одна сессия | `unica.view {}` → каталог этой сессии |
| 5 | Две сессии | разные `workspaceRoot` одновременно |
| 6 | `unica.search` | находит символы только своей кодовой базы |
| 7 | `unica.check` | BSL-диагностика отвечает `passed` или реальными нарушениями |
| 8 | Процессы | по процессу на каталог, простой завершается |
| 9 | Откат | `UNICA_VERSION=v0.15.0.2 sh` возвращает MCP-режим |

## 5. Диагностика

**Инструментов `mcp__unica__*` нет в сессии.**

1. `dsh --version` — нужен DSH 0.2.2-rc.1 или новее (мосту нужен сервис
   `ctx.workingDirectory`).
2. `grep -n "unica-native" ~/.dsh/profiles/<профиль>/cordis.patch.yml` — строка есть?
3. Запустите `node host/selftest.js --cwd /каталог` — если он падает, проблема не в
   DSH, а в рантайме/кэше.
4. Перезапустите DSH: патч профиля читается только при старте.

**`unica.view {}` возвращает чужой каталог.**

Сессия открыта не там, где вы думаете: выполните `pwd` инструментом `bash` в той
же сессии. Мост берёт каталог из `ctx.workingDirectory` сессии, а не из процесса
DSH. Если `pwd` верный, а `workspaceRoot` другой — это дефект моста, сохраните
оба значения.

**Дубли инструментов / два набора.**

В патче осталась строка `mcp-unica`. Удалите её (установщик `0.15.0.3` делает это
сам при установке) и перезапустите DSH.

**`open daemon provider state root: Not a directory (os error 20)`.**

Unica не принимает state root, в пути которого остался симлинк (классика — macOS
`/tmp` → `/private/tmp`), либо каталог недоступен. Установщик и мост
канонизируют пути; если ошибка осталась — перенесите кэш в реальный путь:
`node install.mjs --cache-dir ~/.dsh/unica-native-cache --verify`.

**`native check` падает на холодном кэше.**

Первый запуск скачивает рантайм; бюджет на холодный кэш — 30 минут. Повторите
`--verify`: скачанное сохраняется.

**`verify-install.mjs` падает на Desktop.**

Ревизия `0.15.0.3` находит чанк `dump-config-*` в `app.asar` по имени; если
падает — проверьте `dsh --version` и пересоберите установку из текущей ветки.

## 6. Откат

```sh
gh api -H "Accept: application/vnd.github.raw+json" \
  repos/malinovme/dsh-unica/contents/install.sh | UNICA_VERSION=v0.15.0.2 sh
```

Ревизия `0.15.0.2` — последняя с MCP-строкой: один каталог на профиль, пин через
`cwd`/`UNICA_WORKSPACE_ROOT`, переключение проекта — правкой патча и рестартом.

Удаление native-режима вручную — убрать строки `unica-native` и
`skill-filesystem-unica` из патча профиля и перезапустить DSH; кэш и состояние
демона лежат в `$DSH_HOME/unica`.
