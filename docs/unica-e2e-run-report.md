## Что заблокировано: платформа не проходит через v8-runner

| Шаг | Что произошло |
|---|---|
| `unica.run {op:"infobase.create", dryRun:true}` | **план получен**: `action: "create"`, `connectionFrom: v8project.yaml`, `requiresPlatform: true` |
| `unica.run {op:"infobase.create", dryRun:false}` | через 193 с — `task_transport_failed`, «Task transport is unavailable». Файловой базы нет |

Диагностика цепочки:

1. `unica` действительно запускает раннер и платформу:
   `v8-runner.exe --config ...\v8project.yaml --json-message infobase create`
   → `1cv8.exe CREATEINFOBASE File='...\build\ib'`. Оба процесса живы, база не
   появляется, диалогов нет, процессов не отпускает.
2. **Платформа сама по себе работает**: тот же `CREATEINFOBASE` из шелла создаёт
   базу за 5,4 с (и с `/Out`, и без него).
3. **Стандартный ввод-вывод не виноват**: из Node с `stdio: 'pipe'` — 5 с, с
   унаследованным stdio — 5 с, с урезанным окружением (только `SystemRoot`,
   `TEMP`, `PATH`, `USERPROFILE`) — 5 с.
4. **Висит сам раннер**: `v8-runner.exe … infobase create`, запущенный напрямую из
   шелла, не завершился за 5+ минут (пришлось снимать).
5. Повтор после удаления `build/` с замками — тот же результат, значит это не
   залипший lock от первой попытки.

Вывод: дефект в `v8-runner 0.14.0` на этой связке (Windows 11 + 1С 8.3.27.2325),
а не в порте и не в unica: порт лишь доставляет бинарь, `unica` строит правильный
план, а раннер не доводит вызов платформы до конца.

Проверить гипотезу «дело в контексте DSH» не удалось: раннер висит и вне unica, но
всё ещё под процессом, запущенным из DSH. Чтобы закрыть вопрос окончательно,
нужен запуск из обычной консоли вне DSH — это следующий шаг.

## Следствия для плана

- Разделы 1, 3, 4, 5, 6 (авторинг) и 7.1 проходят полностью.
- Раздел 2 (база), а с ним 6.4, 7.3 (запуск клиента, Vanessa) заблокированы
  раннером; до его починки эти шаги проверяются только как «превью даёт план».
- `unica.check` по BSL-модулям остаётся красным по известной причине: фикс
  #1365 не попал в опубликованный 0.13.0 (см. `issue-check-bsl-comment.md`).
- Написание корня `Configuration.xml` руками даёт `[ERROR] 2. InternalInfo:
  missing` в `check` по конфигурации. Это ожидаемо для скелета, но в сценарии
  стоит либо добавить шаблон с `InternalInfo`, либо записать находку как норму.
