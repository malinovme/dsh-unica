# Почему `infobase.create` зависает: что проверено

Дата: 05.11.2026. Платформа 1С 8.3.27.2325, unica 0.15.0-rc.1, `v8-runner` 0.15.3,
проект `.dsh-cache/e2e/p1`, DSH с полным доступом к файлам.

## Симптом

`unica.run {op:"infobase.create", args:{}, dryRun:false}` не завершается: через
~140–300 с приходит `task_transport_failed`, файловой базы `build/ib/1Cv8.1CD`
нет. Дочерний `1cv8.exe` при этом жив и **жжёт процессор**: 46 с → 209 с → 299 с
CPU за время наблюдения. Окна у процесса есть, но все скрытые
(`V8ValidationMessageWnd`, `V8ToolTipWindow`, `IME`) — модального диалога нет.

Раннер видит то же самое: `build/logs/mcp/actions.log`

```
DEBUG locating platform utility utility=Ibcmd        ← ibcmd в этой сборке нет
DEBUG platform utility resolved utility=V8 path=...\bin\1cv8.exe
DEBUG [Инфобаза] Подготовка: ...\p1\build\ib
DEBUG running process command="...\1cv8.exe CREATEINFOBASE File='...\p1\build\ib'" safety=CriticalNonAbortable
```

и дальше — тишина. `--log-level trace` и `--json-message` собственного вывода
раннера не дают: он ждёт платформу.

## Что исключено (каждый вариант — отдельный прогон)

| Вариант | Как проверял | Итог |
|---|---|---|
| Прямой вызов из шелла | `1cv8.exe CREATEINFOBASE ...` + `/Out` | **5,4 с, база создана** |
| stdio = pipes | Node, `stdio: ['pipe','pipe','pipe']`, поток не читаю | **5 с** |
| stdio = inherit | Node, `stdio: 'inherit'` | **5 с** |
| Консоли нет | Node, `detached: true`, `stdio: 'ignore'`, `windowsHide` | **5 с** |
| Урезанное окружение | только `SystemRoot`, `TEMP`, `TMP`, `PATH`, `USERPROFILE` | **5 с** |
| Плохой `TEMP` | `TEMP`/`TMP` → несуществующий каталог / пусто / удалено | падает **быстро**, не висит |
| Путь в форме `\\?\C:\...` | `File='\\?\C:\...'` | **5 с** |
| Рабочий каталог раннера | `cwd = ...\p1\build` (с его lock-файлами) | **5 с** |
| Форма аргументов | одной строкой и двумя аргументами | **5 с** в обоих случаях |
| Замки от прошлых прогонов | удаление `build/` перед прогоном | не влияет |
| Версия раннера | 0.14.0 и 0.15.3 | висит одинаково |
| Песочница DSH | полный доступ (`danger-full-access`) | висит и там |

Итог: **воспроизвести зависание вне раннера не удалось ни одним способом.**
Команда, каталог, аргументы, окружение, stdio и консоль — те же, что у раннера,
но база создаётся за 5 секунд. Значит причина внутри того, как `v8-runner`
запускает платформу, а не в конфигурации проекта, платформе или DSH.

## Побочная находка: песочница `workspace-write` ломает платформу

Под `workspace-write` платформа не может писать в свой профиль:

```
write to C:\Users\User\AppData\Roaming\1C  → Отказано в доступе
write to C:\Users\User\AppData\Local\1C    → Отказано в доступе
```

`1cv8.exe` в ответ падает сразу, с кодом `-532462766` (`0xE0434352`, .NET
исключение), не создаёт базу и не пишет `/Out`-лог. То есть **любая** работа с
информационной базой требует полного доступа к файлам: `workspace-write`
недостаточно. Это стоит держать в README порта — иначе первый же запуск
платформы выглядит как «необъяснимое падение 1С».

## Что осталось непроверенным

1. Стек зависшего потока. Потоков 16: семь в `Wait, UserRequest`, пять в
   `Wait, EventPairLow`, один `Running`. Именно `Running` жжёт CPU. Без отладчика
   (WinDbg/ProcDump, требуют установки) стек не снять.
2. Захват пакетов на время зависания: если 1С ищет лицензию по сети, это будет
   видно в трафике.
3. Запуск `v8-runner` из консоли **вне DSH**. Сейчас проверено «вне unica», но
   под процессом DSH; это последняя оставшаяся разница окружения.

## Что это значит практически

- Платформенная часть сценария (`infobase.create`, `push`, `launch`, Vanessa)
  блокирована дефектом раннера, а не портом: порт лишь доставляет его бинарь,
  `unica` строит правильный план, `1cv8` из любого другого процесса создаёт базу.
- Обхода на нашей стороне нет: `ibcmd` в этой установке отсутствует (платформа
  поставлена клиентским комплектом), `providers` его всё равно не найдёт.
- Для апстрима доказательная база готова: таблица выше плюс `actions.log` с
  точной командой и `safety=CriticalNonAbortable`.

## Обновление: поставили `ibcmd` — и картина изменилась

Платформа была поставлена клиентским комплектом, без `ibcmd`. Доустановили
компонент «Сервер 1С:Предприятия» (`CSServer`) — `ibcmd.exe`, `ibcli.dll`,
`ibsrv.exe` появились в `C:\Program Files\1cv8\8.3.27.2325\bin`, установщик
создал каталог данных `%LOCALAPPDATA%\1C\1cv8\standalone-server` с подкаталогами
(`perf-data`, `ipc-data`, `temp`, `users-data`, `log-data`, `session-data`).
Попутно выяснилось, что `CSClient`, который я советовал первым, к `ibcmd`
отношения не имеет: MSI ставил его с кодом 0, а компонент `CS_AServer` оставался
`Absent`.

**`ibcmd` работает**: прямой вызов создаёт базу за секунду.

```
[INFO] Создание информационной базы...
[INFO] Создание информационной базы успешно завершено
[INFO] Импорт конфигурации из XML...
```

Импорт при этом падает — но уже по делу: наш скелет `Configuration.xml` не имел
узла `InternalInfo` (`Отсутствует внутренняя информация (узел InternalInfo) для
объекта Configuration`). Узел добавлен; `unica.check` жаловался ровно на это.

## Что осталось: раннер запускает платформу несовместимым способом

Через `v8-runner` тот же `ibcmd` падает за 150–230 мс:

```
Ошибка указания пути к файлу блокировки каталога данных сервера:
C:/Users/User/AppData/Local/1C/1cv8/standalone-server/lock.pid
```

Проверено и исключено:

| Проверка | Результат |
|---|---|
| `ibcmd` напрямую из PowerShell | **создаёт базу** |
| `ibcmd` из Node (pipes, stdin pipe, NUL, `windowsHide` вкл/выкл) | **создаёт базу** |
| три вызова подряд без паузы (гонка за `lock.pid`) | все успешны |
| ACL и владелец каталога данных | `FullControl`, запись из шелла проходит |
| окружение ребёнка раннера (снято обёрткой) | полное: `PATH`, `TEMP`, `APPDATA`, `SESSIONNAME`, `DSH_*` |
| аргументы ребёнка (снято обёрткой) | ровно семь, совпадают с ручными |
| рабочий каталог ребёнка | `C:\Projects\dsh_test`, как у ручного запуска |
| токены процессов (`unica`, `node`, шелл) | одинаковые, без групп песочницы |
| независимый запуск тем же способом (C#-обёртка) | **та же ошибка** |

То есть ломается не проект, не конфигурация и не `ibcmd`, а **сам способ запуска
дочернего процесса**: PowerShell и Node его переживают, а два независимых
лаунчера (Rust-раннер и моя C#-обёртка) приводят к одному и тому же отказу 1С на
файле блокировки каталога данных. Причину внутри 1С это уже не раскрывает —
нужен либо стек процесса (WinDbg), либо фикс на стороне раннера.

## Что из этого следует для сценария

- Всё, что делает `unica` без платформы, работает: метаданные, формы, поиск,
  справка, `check`, `diff`.
- Платформенные шаги (`infobase.create`, `push`, `launch`, Vanessa) пока
  выполняются только вручную через `ibcmd`/`1cv8`; через порт они упираются в
  дефект раннера.
- Для апстрима теперь два независимых наблюдения: зависание `1cv8` и отказ
  `ibcmd` на `lock.pid` — оба воспроизводятся только при запуске из раннера.

## Контрольная проверка на чистой установке (Codex) — дефект не воспроизвёлся

Проверка на другой машине с той же связкой (Unica 0.15.0-rc.1 + `v8-runner`
0.15.3) дала:

- `unica.run infobase.create` создал изолированную файловую базу — ошибка
  `standalone-server/lock.pid` **не воспроизвелась**;
- `unica.run make` собрал и проверил CF — запуск платформы не завис;
- операции «как `v8-runner check`» в публичном `unica.run` нет, поэтому зависание
  именно на `/CheckConfig` этой проверкой не исключено;
- на той машине первый запуск тоже спотыкался о служебный каталог Unica с плохими
  правами и прошёл после его пересоздания.

Вывод: **дефект не универсален, а специфичен для окружения DSH на этой машине.**
Раннер сам по себе платформу запускает нормально.

## Найденное различие: целостность процесса и запись вне рабочего каталога

1. Токен зависшего `1cv8`, запущенного раннером: `AppContainer=false`,
   capabilities=0, 11 групп, **integrity `S-1-16-4096` (medium)**.
   Токен моего шелла при этом: **`S-1-16-8192` (high)**. Набор групп одинаковый.
2. Проба-исполняемый файл, запущенный как потомок инструмента, не может писать
   **никуда, кроме рабочего каталога**:

```
write FAIL C:\Users\User\AppData\Local\1C            UnauthorizedAccessException
write FAIL C:\Users\User\AppData\Local\1C\1cv8       UnauthorizedAccessException
write FAIL C:\Users\User\AppData\Local\Temp          UnauthorizedAccessException
write OK   C:\Projects\dsh_test\.dsh-cache\e2e\p1\build
mkdir FAIL ...\1C\1cv8\probe-dir-test                UnauthorizedAccessException
```

3. При этом из самого процесса инструмента (pwsh) и из его прямого потомка
   (`node`) запись в те же пути **проходит**. То есть ограничение избирательное:
   не «пользователь не может», а «этот конкретный процесс не может».

Это и есть причина обоих симптомов: 1С нужен `%LOCALAPPDATA%\1C\1cv8`
(каталог данных автономного сервера), запись туда запрещена — `ibcmd` сообщает
`access denied` / `lock.pid`, а `1cv8` уходит в цикл и жжёт CPU вместо ошибки.
Чистое окружение Codex такой запрет не ставит, поэтому там всё работает.

## Настоящая причина: Low-метка наследуется на кэш внутри рабочего каталога

`4096` — это **Low** (а не Medium, как я решил сначала): `0x1000` Low, `0x2000`
Medium, `0x3000` High. У шелла и у процесса DSH — `8192` (Medium), у `1cv8`,
запущенного раннером, — `4096` (Low).

`icacls` показал, что файлы в рабочем каталоге несут унаследованную метку
`…:(I)(NW)` — Low. Песочница DSH помечает рабочий каталог Low и ставит
capability-ACE `S-1-4-…:(W,D,DC)`; всё, что создаётся внутри, наследует и ACE, и
метку. Дальше действует правило Windows: **исполняемый файл с Low-меткой
запускается с Low-токеном**, даже если родитель Medium. Low-процесс не может
писать в объекты Medium — а профиль пользователя именно Medium.

Наш кэш рантайма лежал в `C:\Projects\dsh_test\.dsh-cache\runtimes`, то есть
внутри рабочего каталога. Значит `v8-runner.exe` оттуда запускался Low, и всё его
потомство (`1cv8`, `ibcmd`) тоже Low — отсюда и «доступ запрещён», и
`lock.pid`, и зависание `1cv8`.

### A/B-проверка

| Кэш рантайма | Целостность раннера | Результат `infobase.create` |
|---|---|---|
| `…\dsh_test\.dsh-cache\runtimes` (в рабочем каталоге) | **Low (4096)** | `ibcmd`: `access denied` / `lock.pid` |
| `C:\Users\User\.dsh\port-cache\runtimes` (вне каталога) | **Medium (8192)** | база **создана**, дальше только ошибка импорта XML |

Тот же `icacls` на скопированном раннере метки Low уже не показывает — она не
переезжает вместе с файлом, а наследуется только при создании внутри помеченного
каталога.

## Что делать с этим

1. **Кэш рантайма держать вне рабочего каталога.** Значение по умолчанию у порта
   (`$DSH_HOME/unica/runtimes`) как раз снаружи; ловушка возникает, если указать
   `--cache-dir` внутрь проекта. Предупреждение добавлено в README порта.
2. Дополнительно это стоит знать всем, кто собирает что-то в рабочем каталоге и
   потом это запускает: Low-метка снижает целостность процесса. Для DSH это
   ожидаемое поведение песочницы (задокументировано в
   `dsh-sandbox-windows-acl`), а не дефект.
3. Платформенные шаги больше не нужно выносить из DSH — достаточно, чтобы раннер
   лежал вне помеченного каталога. Проверено на `infobase.create`.

## Отдельная находка: лицензия 1С

После установки серверных компонентов `1cv8 DESIGNER` перестал работать без
лицензии:

```
Не найдена лицензия. Не обнаружен ключ защиты программы
или полученная программная лицензия!
```

`ibcmd` при этом базу создаёт (лицензия ему не нужна), а `DESIGNER` — нет.
`C:\ProgramData\1C\licenses` пуст, службы HASP/Sentinel не установлены. Значит
`push`, `launch` и `DumpConfigToFiles` на этой машине заблокированы лицензией, а
не кодом — это нужно закрыть ключом защиты или программной лицензией.
